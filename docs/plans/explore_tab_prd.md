## Problem Statement

CARD Catalog stores nine separate tables — Resources, Publications, Code Repositories, Datasets, Supplementary Files, Grants, Software, Models, SciLite Annotations, and Human Cellular Models — each as its own page with its own filters and, on four of them, its own single-table Knowledge Graph. A researcher studying a specific gene or disease, or a program officer assessing a portfolio, needs to answer questions that span *all* of these at once ("what datasets, code, publications, and cell lines relate to APOE?"), but today that means manually cross-referencing PMC links, Resource Names, and gene symbols by hand across up to nine separate pages. There is no way to start from one value and see everything else in the catalog that connects to it.

## Solution

A new **Explore** page, additive to the existing per-table pages (which are unaffected and keep their own single-table Knowledge Graph views). A user picks a starting table, an attribute on that table, and a specific value (e.g. `Gene = APOE`) to get a focused seed node set — never a whole unfiltered table dumped onto the canvas. From there, they add one additional table at a time; each addition requires picking which attribute on the current graph and which attribute on the new table should connect them, with an auto-suggested pairing offered whenever an obvious correspondence exists (e.g. `source_url` on Datasets/Supplementary Files/Grants/Software/Models against `PubMed Central Link` on Publications) — but always user-confirmed, never silently assumed. The original seed value keeps filtering every subsequent addition unless the user explicitly clears it. If a step would match more rows than can be shown legibly, the tool displays an honest capped count (e.g. "showing 60 of 3,412 — refine to narrow") rather than truncating silently or blocking the action outright. The most recent addition can be undone; anything more tangled means starting over.

## User Stories

1. As a catalog user, I want to see the column schema of all nine tables immediately when I open Explore, so that I know what attributes are available to build with before committing to any data load.
2. As a catalog user, I want browsing table schemas to cost no network requests, so that I can freely look around without waiting.
3. As a catalog user, I want to pick a starting table for my seed, so that I can begin from whichever table is most relevant to my question.
4. As a catalog user, I want to pick a specific attribute on my starting table, so that I can narrow to the dimension I actually care about (a gene, a disease, a study name, etc.).
5. As a catalog user, I want to search a table's actual values for a chosen attribute (not just its schema), reusing the same searchable "Search N values…" experience the existing filter sidebars already provide, so that finding a specific value like "APOE" feels familiar and fast.
6. As a catalog user, I want a table's data to load only the first time I actually select it, so that I don't pay the transfer/parse cost of tables (especially the very large SciLite Annotations table) I never touch in a session.
7. As a catalog user, I want to see a loading state while a table's data is being fetched for the first time, so that I understand why there's a brief delay after picking a new table.
8. As a catalog user, I want to pick one specific value from my chosen attribute (e.g. `Gene = APOE`) as my seed, so that my starting node set is focused rather than the entire table.
9. As a catalog user, I want my seed node set rendered immediately after I pick a value, so that I can confirm it's the starting point I expected before building further.
10. As a catalog user, I want to add a second table to my graph, so that I can see how my seed connects to other kinds of catalog data.
11. As a catalog user, when I add a new table, I want to be asked which attribute on my current graph and which attribute on the new table should be used to connect them, so that the join is explicit and I understand exactly why two rows are considered related.
12. As a catalog user, I want the tool to suggest an attribute pairing automatically when an obvious correspondence exists (e.g. `source_url` ↔ `PubMed Central Link`), so that I don't have to already know the underlying schema relationships myself.
13. As a catalog user, I want to be able to override any auto-suggested attribute pairing, so that I'm not stuck with a guess that doesn't match what I actually want to explore.
14. As a catalog user, I want to always see which attribute pairing was actually used for a given connection, so that a wrong or surprising auto-suggestion is never applied silently.
15. As a catalog user, I want to keep adding tables one at a time, each building on the current state of the graph, so that I can construct a multi-hop view (e.g. Resources → Code Repositories → Publications → Human Cellular Models) incrementally.
16. As a catalog user, I want my original seed value to keep filtering every subsequent table I add, so that my graph stays focused on my original question instead of drifting into unrelated matches introduced by a later hop.
17. As a catalog user, I want the option to explicitly remove my seed constraint partway through, so that I can deliberately broaden the graph once I've established the initial context I wanted.
18. As a catalog user, when a hop would match far more rows than can be shown legibly, I want to see an honest count of how many total matches exist versus how many are actually displayed (e.g. "showing 60 of 3,412"), so that I know the graph is a sample, not the complete picture.
19. As a catalog user, I want the tool to never silently truncate a large match set without telling me, so that I never mistake a partial view for a complete one.
20. As a catalog user, I want the tool to never outright block a hop just because it has high fan-out, so that I can still choose to proceed with a capped view of a genuinely broad relationship (e.g. a well-studied gene).
21. As a catalog user, I want a way to narrow an oversized hop (e.g. by adding an additional attribute filter) before or after it's added, so that I have a path to a more precise result instead of just accepting the honest-but-large count forever.
22. As a catalog user, I want to undo the single most recently added table/hop, so that I can correct a mistake or discard a hop whose results turned out to be unhelpful clutter.
23. As a catalog user, I want a full "start over" action, so that I have a simple fallback whenever a mistake is more than one step back and undo-last-hop isn't enough.
24. As a catalog user, I want nodes from different tables to be visually distinguishable (e.g. by color), so that I can tell at a glance which kind of catalog record I'm looking at in a mixed, multi-table graph.
25. As a catalog user, I want to hover over or click a node to see the underlying row's details, consistent with how the existing single-table Knowledge Graph pages already show per-node info, so that I don't have to leave the graph to understand what a node represents.
26. As a catalog user building a graph that includes Code Repositories, I want to understand that only repositories discovered via a paper mention (not those found via direct GitHub search) can connect to a specific Publication, so that I'm not confused when roughly half of Code Repositories rows have no publication-level connection available.
27. As a catalog user building a graph that includes Human Cellular Models, I want the tool to offer `Gene` (not `dbSNP`) as the default/primary way to connect to SciLite Annotations and onward to Publications, so that I get the join path with real, usable coverage (94% of rows) rather than the sparse one (18% of rows).
28. As a catalog user, I want multi-value fields (semicolon-delimited columns like Diseases Included or Genes / Proteins) to be split correctly during matching, so that a row with several diseases or genes listed can still correctly match on any one of them.
29. As a catalog user, I want value matching to be case-insensitive and trimmed of stray whitespace, so that trivial formatting differences between tables don't cause real matches to be missed.
30. As a program officer, I want to seed on a Resource or funding-related attribute and chain outward through Code Repositories and Publications, so that I can assess a specific portfolio's footprint across the catalog without manually cross-referencing pages.
31. As a biomedical researcher, I want to seed on a specific gene and chain through Datasets, Code Repositories, Publications, and Human Cellular Models in whatever order matters to my question, so that I can discover the full set of related resources for a hypothesis I'm investigating.
32. As a catalog user, I want Explore to be reachable as its own top-level navigation item, so that it doesn't get buried inside an existing table's page.
33. As a catalog user, I want the existing per-table Table/Browse/Graph views to remain unchanged and unaffected by Explore, so that workflows I already rely on keep working exactly as before.

## Implementation Decisions

- **New page, additive**: Explore is a new top-level page/route, not a replacement for any existing page or its per-table Knowledge Graph view. Existing pages (Resources, Publications, Code Repositories, Human Cellular Models) keep their current Table/Browse/Graph[/Trends] views untouched.
- **Client-side only, no backend dependency**: consistent with the app's current architecture (client-side TSV fetch + in-browser filtering), Explore does not depend on the Postgres/API migration work tracked separately. All joins and matching happen in the browser against data loaded via the existing per-table loader functions.
- **Table-metadata registry (new, shared module)**: a single source of truth listing, per table, its column schema and which columns are multi-value fields with their delimiter (";" almost everywhere, "," for Coarse Data Modality specifically). This consolidates information currently duplicated across each page's own facet configuration and the Docs page's schema listing, and is what powers Explore's always-visible schema browsing (decision below) without requiring any table's data to be loaded.
- **Schema vs. data loading split**: table schemas (column names) for all nine tables are available immediately from the metadata registry, at zero network/data cost. A table's actual row data — and the searchable value list for a chosen attribute — is fetched (via the existing per-table loader) only the first time that table is selected, and kept in memory for the remainder of the session.
- **Seed model**: the seed is (table, attribute, value). Selecting a seed loads that table (if not already loaded), filters to rows where the chosen attribute contains the chosen value (respecting multi-value splitting), and renders the result as the initial node set.
- **Hop model — join/match engine (deep module, testable in isolation)**: a hop is (new table, current-side attribute, new-table-side attribute). Given the current graph's node set and the newly loaded table's rows, the join/match engine computes matches by treating both sides' chosen attribute as a set of values (splitting multi-value fields by their known delimiter, trimming whitespace, comparing case-insensitively) and connecting any pair whose value sets intersect. This is a generalization of the existing single-table Knowledge Graph's shared-attribute-overlap logic to two different row types instead of one. The engine's interface takes two row collections plus attribute/delimiter info and returns matched pairs plus a total-match count; it has no dependency on rendering and does not know about React.
- **Auto-suggested attribute pairing**: when adding a new table, the current-side and new-table-side attribute pickers default to a known-good pairing if the metadata registry has one on record for that table pair (e.g. `source_url` ↔ `PubMed Central Link` for Datasets/Supplementary Files/Grants/Software/Models; `Resource Name` for Code Repositories/Resources; `Gene` for Human Cellular Models via SciLite Annotations). The suggestion is always overridable via the same picker UI, and the actually-selected pairing is always visibly labeled on the resulting connection — an auto-suggestion is never applied without being shown.
- **Seed persistence as a standing filter**: the seed's (attribute, value) constraint is tracked independently of hop history and re-applied whenever it's structurally possible on a newly added table (i.e., when the new table also has a compatible attribute), narrowing that hop's results further. Removing the seed is an explicit, separate user action from undoing a hop.
- **Graph state reducer (deep module, testable in isolation)**: owns seed state, ordered hop history, and an undo-last-hop operation; derives the current node/edge set by replaying seed + hops via the join/match engine. Actions: set seed, clear seed, add hop, undo last hop, reset. This is a pure state machine with no rendering dependency, deliberately kept separate from the join/match engine so hop/seed/undo semantics can be tested independently of matching logic.
- **Fan-out cap with honest count**: each hop caps the number of newly rendered nodes (the existing single-table Knowledge Graph already caps at a default `maxNodes`; Explore reuses the same style of cap per hop) but always displays the true total match count alongside the capped/shown count. Never silently truncates, never blocks a hop outright regardless of match size.
- **Undo scope**: only the most recently added hop can be undone; there is no operation to remove an arbitrary earlier hop while keeping later ones. A full reset (clear seed and all hops) is always available as a fallback.
- **Node/edge rendering**: nodes are color- or otherwise visually coded by originating table so a mixed multi-table graph stays legible; per-node hover/click detail reuses the existing Knowledge Graph pages' node-info pattern rather than introducing a new one.
- **Known per-table join caveats surfaced, not silently hidden**: Code Repositories' `Source` attribute is only a valid Publications-join key for the subset of rows where it holds a PMC link (roughly half); rows where it instead holds GitHub-search discovery-method text simply have no Publications-side match, and the join/match engine treats that as a normal no-match case rather than an error. Human Cellular Models' `Gene` is the default/suggested join to SciLite Annotations (and onward to Publications); `dbSNP` remains available as attribute if a user explicitly picks it, but is not the auto-suggested default given its much lower match coverage.

## Testing Decisions

- **What makes a good test here**: tests target the join/match engine and graph state reducer purely through their public input/output contracts (given these rows and this attribute pair, assert on the resulting matches/count; given this sequence of seed/add-hop/undo actions, assert on the resulting graph state) — never asserting on internal data structures or intermediate representation that could change without changing behavior.
- **Modules to test**: the join/match engine (multi-value splitting, case/whitespace normalization, match-count correctness, zero-match handling) and the graph state reducer (seed set/clear, hop add/undo-last, seed persistence across hops, reset). Both are pure, React-free modules by design specifically so they can be tested this way.
- **Prior art**: none — `web/` currently has zero test files and no test runner configured. This is the first frontend test infrastructure in the project. Vitest is the natural minimal-friction choice given the app is already Vite-based, but introducing it is itself a new decision for this feature, not something with existing in-repo precedent to follow.

## Out of Scope

- AI Analysis panel for Explore (deferred to v2) — the existing per-page AI Analysis pattern assumes a fixed, known row shape, which doesn't fit a graph whose shape changes with every hop; needs its own design once real usage patterns are known.
- URL-shareable/persistable graph state (deferred to v2).
- Removing or editing an arbitrary hop mid-chain while keeping later hops — only last-hop undo and full reset are supported.
- A curated/guided seeding experience limited to Disease and Gene attributes specifically — rejected in favor of a fully generic any-table/any-attribute picker.
- Any change to the existing per-table pages' own Table/Browse/Graph[/Trends] views — Explore is purely additive.
- Any backend, API, or database changes — this is a client-side-only feature built against the current flat-file architecture.
- Fixing the underlying data-quality gaps this feature surfaces (Code Repositories' partial Source-to-Publications coverage, Human Cellular Models' weak dbSNP-based coverage) — Explore reflects these honestly (via capped/suggested defaults) rather than attempting to repair the source data as part of this work.

## Further Notes

- Verified real join keys across tables (established via direct data investigation, not assumption): Publications' `PubMed Central Link` is the effective hub. Datasets, Supplementary Files, Grants, Software, and Models all join to it via their own `source_url` (~100% populated, clean). Code Repositories joins to Resources via `Resource Name` (always present) and only *sometimes* to Publications via `Source` (≈55% of rows — the rest is discovery-method text, not a link). SciLite Annotations joins to Publications directly via `PMC ID`. Human Cellular Models joins to SciLite Annotations (and onward to Publications) via `Gene` matched against SciLite's `Gene_Proteins`-type annotations (≈94% row coverage) — its `dbSNP` column also technically matches SciLite's `Accession Numbers` type, but only covers ≈18% of rows and should not be the default path.
- Real fan-out risk is not hypothetical: common gene symbols and disease names are known (from this session's own data checks) to produce match counts in the thousands via SciLite, which is exactly the scenario the honest-capped-count behavior needs to handle well rather than as an edge case.
- The table-metadata registry this feature introduces duplicates/consolidates information currently scattered across each existing page's own facet configuration (`FACETS` arrays) and the Docs page's schema listing; migrating those existing pages to consume the same registry is a reasonable future cleanup but is not required for this feature to ship.
- This feature was scoped via a structured requirements interview (grill-me) covering purpose, seeding, chaining, join mechanics, seed persistence, fan-out handling, and undo — see prior conversation for the full decision trail if any of the above needs re-litigating.
